# 新脊椎審查端指引

審查端的輸出有兩部分，它們的權力不一樣：

- **機械判定會擋。** 它由 exit code 承載，不需要讀者同意。
- **判斷報告不擋。** 它是帶引用的意見，由人裁。

把兩者混在一起是這條流程要避免的事。需要語意判斷的東西一旦進了 fail-closed 的閘，閘就
不再乾淨——它開始擋一些沒人能精確定義的東西，然後大家學會繞過它。

## 機械判定

機械判定是「執行 oracle」這個閘。它做三件事：

1. 用 `scripts/frozen-assertion-fence.sh verify` 確認斷言沒被動過。封條對不上就停，
   要人重簽——這時審查根本還沒開始，因為成功的定義本身變了。
2. 用 `scripts/run-hardened-oracle.sh` 跑量測命令。判定同時看 exit code 與正向證據：
   命令得真的跑起來、真的量到東西。exit 0 而沒有正向證據不是通過。
3. 用 `scripts/record-measurement-change.sh verify` 確認手上這條量測命令是登錄過的。
   換過而沒帶紅過證據的命令不被承認。

任一項不成立，機械判定就是非 PASS，這件事沒有討論空間。

## 判斷報告

判斷報告處理只能是散文、無法被執行的部分。它的結論一律引用具體 `path:line`——沒有引用的
斷言在報告裡沒有份量，這跟 friction log 的 `contract_evidence[]` 是同一條紀律。

報告不產生 PASS / FAIL。它產生的是「我讀了這段，依據是這幾行，我的判斷是這樣」，交給人
決定要不要處理。

## 驗證強度分三層

不同對象用不同強度，不可以一律降到最弱那層：

| 強度 | 適用對象 | 方法 |
|---|---|---|
| 可注入 | 會被機械執行的部分 | 刻意構造情境，觀察結果 |
| dogfood 觀察 | loop 行為 | 跑真工作記錄，樣本薄就如實標示 |
| 靜態檢視 | 只能是散文的部分 | 讀指定段落，判斷條件是否成立 |

「一律靜態檢視」看起來省事，實際上是把可以被證偽的東西降級成不能被證偽的東西。可注入的
就注入。

## 正負兩表都要驗

只有負向表列時，「什麼都不做」可以拿滿分。只有正向表列時，副作用沒人管。

可注入的斷言尤其要兩向都跑：只有反例的驗證，一個永遠回 FAIL 的審查端也會全綠。正例要能
證明真達標的交付確實被判 PASS。

## dogfood 結論的強度

dogfood 觀察的樣本通常很薄，而且觀察者往往同時是被觀察者。這不使結論無效，但它使結論不是
統計證據。報告要如實標示樣本數與觀察者身分，不要把「跑過一次」寫成「已驗證」。
