# 一份報告的段落骨架

需要交出去給人讀、讀完要做決定的東西，都照這個骨架寫：研究報告、調查結果、檢查結果、
市場分析、異常排除、追蹤報告。五種產出共用同一組段落，只有第三段會換。

## 五段

```
1. 結論      結果一句話，加上要讀的人決定什麼。只讀這一段就能開始討論
2. 根據      支撐第 1 段的證據，逐條可追
3. 主體      隨報告類型換，見下
4. 待決      要人拍板的，每一項帶自己的建議與理由
5. 限制      沒驗到的、樣本薄的、不要拿去引用的
```

第 3 段是五種產出唯一不同的地方：

| 這份報告是 | 第 3 段寫 |
|---|---|
| 研究、調查 | 方法與樣本：怎麼查的、看了哪些、樣本多大 |
| 檢查結果 | 逐項判定：每一項過了沒、依據是哪一行 |
| 市場分析 | 區隔與競品：對照組是誰、拿什麼比 |
| 異常排除 | 時間軸與根因：什麼時候開始、怎麼發現、根因是什麼、怎麼擋住的 |
| 追蹤報告 | 狀態表：每一張單、每一件事落在已處理／進行中／觀察中／要請人看其中一格，見下 |

### 追蹤報告：每天或每週更新的那一種

同一件事每隔一段時間更新一版，讀的人每次要知道的是：手上有哪些事、各自走到哪、誰在等誰。
這一類最容易長成按資料類別排的一疊表格——每一節都對，讀完說不出現在有哪些事在進行。所以它
的形狀從三個外面在用的寫法組起來：

**讀者是團隊，不是委託人。** 這份報告會被轉給大家看，所以委託人要裁的事不進報告，寫在給
委託人的回覆裡。一格「待決」放進報告，等於把只有一個人要回答的問題攤給所有人，而團隊讀到
那一格也不能做什麼。

- **頁首照 BLUF 寫**（bottom line up front，美軍公文規範 AR 25-50，
  [摘要](https://en.wikipedia.org/wiki/BLUF_(communication))）：一行結論。BLUF 原文還要寫出
  讀的人要做的事；這裡的讀者是團隊，要團隊做的事落在狀態表「要請人看」那一格。
- **狀態表照 PPP 的原意寫**（Progress／Plans／Problems，週期性狀態報告的慣例，
  [說明](https://blog.weekdone.com/management-tools-ppp-plans-progress-problems/)）：做完了
  什麼、接下來在做什麼、卡在哪裡，三件都要有。這裡拆成四格，**這張單底下的每一張子單、每一件事
  落在而且只落在一格**：

  | 格 | 每一項要有的欄位 | PPP 的哪一件 |
  |---|---|---|
  | 已處理 | 做了什麼、結果如何 | Progress |
  | 進行中 | 誰在做、預期結果、到什麼時候 | Plans |
  | 觀察中 | 看哪一個指標、什麼時候判、回到多少算好、到多少算壞 | Plans |
  | 要請人看 | 請誰、要他做什麼、已經卡多久 | Problems |

  一項落不進任何一格，或那一格的欄位缺了，這份報告就還沒寫完。只列「要做的兩件事」不夠：
  讀的人要看得到手上**全部**的事，包括已經處理掉的。
- **當天有事件的那一節照 postmortem 寫**（[Google SRE Example Postmortem](https://sre.google/sre-book/example-postmortem/)）：
  影響、根因、帶負責人的行動。沒有事件就不寫這一節。

**這一種的順序跟通用五段不同**：

```
1. 結論      BLUF：一行結論
2. 狀態表    已處理／進行中／觀察中／要請人看
3. 事件      postmortem：影響、根因、帶負責人的行動。當天沒有事件就不寫
4. 根據      數據與圖表。展開的每一張配一句「這張看什麼」，其餘折疊
5. 限制      同通用五段的第 5 段
```

通用五段把根據放在主體前面，是因為讀的人要先信了結論才決定要不要往下讀。追蹤報告的讀者
每一版都會回來，他要的是「手上有哪些事、各自走到哪、誰在等誰」，信不信結論可以等到要的
時候再展開根據。所以**讀完頁首與狀態表就要說得出每一件事在哪一格，不必經過任何一張圖表**；
把根據排在前面，讀的人要先穿過幾張圖才看得到現況。

量測過程不進報告，進那張單自己的工作紀錄。

## 每一段的規矩

**第 1 段（結論）**：三行以內。有後續動作就寫成有序清單，讀完知道接下來照什麼順序發生。
不要在這裡放自己的推導過程，那是第 2 段。**這一段是整份報告能不能第一版就拿出去討論的
唯一決定因素。**

**第 2 段（根據）**：每一條都要指得出來源，檔案路徑加行號、命令輸出、來源連結三選一。
指不出來的就寫「這一條我拿不出證據」，不要靠語氣撐。

**量測命令從留存的實際 payload 抄，不憑印象重寫。** 報告裡抄錯的命令，會被下一次驗證原樣
拿去跑，而它量到的 0 跟真的 0 長得一樣。幾條命令共用的條件提到表外，只寫一份。

**第 3 段（主體）**：只放上表那一格要的東西。想寫的東西不屬於那一格，通常代表這份報告
其實是另一種類型。

**第 4 段（待決）**：每一項都要帶自己的建議，不要把選項列出來讓人挑。真正互斥、風險輪廓
不同的方向才需要問。沒有東西要人拍板就不寫這一段。

**第 5 段（限制）**：主動說出哪些結論站得比較不穩。跑過一次不等於驗證過，樣本薄就寫出
樣本多大。這一段留白的報告，讀的人只能假設它什麼都驗過了。

**有時程那一欄的報告**（短期、已排上線、預計何時回收）：那一欄只放有具體班次的項目。還沒
動工的、只有目標日的不放進去——目標日不是班次，放進去整欄會被讀成承諾。

**引用一個百分比時，說出它的分母**，以及那個分母在比較的兩個時間點之間有沒有變。分母被
改過的兩個百分比不能相減：拿掉分母裡的一大塊之後，同一件事的佔比會自己變，那個差不是改善。

## 哪幾段可以不寫

第 4、5 段沒有內容就不寫。**沒有內容跟寫一行「無」是兩件事**：寫「無」看起來像檢查過了。

第 1、2、3 段不能不寫。缺哪一段翻一眼看得出來，這就是這個骨架存在的理由——沒有骨架的
散文報告，讀的人沒有東西可以拿來對照，「這份太長」「這份沒重點」講不出是哪裡出問題。

## 它不管什麼

**不管用什麼裝。** 段落與順序歸這裡管，版型、CSS、檔案格式、用什麼工具產出都不歸。同一份
骨架寫成純文字、寫成網頁、貼進任何一個聊天工具都成立。

**不管已經判定完的東西怎麼排版。** 機器判完之後把結果排整齊的那一類產出（逐條 PASS／FAIL
的清單、跑完測試的摘要）不套這個骨架。那裡面沒有要讀的人做的決定，套上去只是多幾個空段落。

**不管有既定格式的文件。** 站會報告、履歷、PR body、規格書、公文各有自己的慣例，慣例優先。
拿這個骨架去蓋掉它們會產出一份看起來很整齊、但沒有人認得的東西。

**不管講話。** 對話回覆的形狀在框架的常駐規則裡，那一份管的是三段（結論／根據／待決），
比這裡短。一份要交出去的報告才走這個骨架。
