# Standup Planning Contract

這份 reference 負責把原始資料整理成每張 epic 的昨日／今日／卡關三格。

**每一格寫多長、什麼語氣，寫在 `standup-template.md` 的〈怎麼寫：產出物精簡，證據不精簡〉**
——那五條在這裡不重講一次，但它們管的正是這一份決定出來的內容。三格是在會議上唸出來給人
聽的，聽的人要的是做了什麼、今天做什麼、卡在哪，不是我怎麼證明的；證據留在單上與 PR 裡。

## 昨日 Merge And Dedup

同一 ticket 同時出現在 git 與 JIRA 時，合併成一行：JIRA status/title 為主，git commit
summary 為輔。

依 ticket 的 parent epic 分組。沒有 parent epic 的活動與會議放進 `其他（無 Epic）`。

Ticket 格式使用 `[KEY title](https://{jira.instance}/browse/KEY) — 動作摘要`。

## Plan Vs Actual

<!-- STANDUP-CONTRACT: plan-vs-actual-source -->

**比對來源是這支 skill 自己每天落下的那份本地檔案**，不是任何一個它已經不再寫入的地方。
取 `{base_dir}/standups/` 底下日期早於今天的最新一份，解析它的**今日**格。

以前這裡讀的是某個外部頁面上「今天以前最近一筆 entry」。那個頁面一換，它就再也沒有新的
entry，於是這一步每天都走進 skip 條件——而 skip 條件在散文裡長得像偶發狀況。**生產者與
消費者現在是同一個檔案**，這一步才不會再靜靜地失效。

**拿哪一份比的要說出來**，每一次都說：

- 有可比的前一份 → 說出是哪一天的哪一個檔案，以及它距離今天幾天。隔了假日或請假是正常的，
  隔了兩個月則是一個要被看到的訊號。
- 沒有可比的前一份 → 說出為什麼（`standups/` 底下沒有更早的檔案／那一份沒有今日格），
  然後照常往下走。**不沉默跳過**：一個安靜跳過的比對，跟一個「比過了、沒有落差」的比對
  在報告上長得一模一樣。

**比的是內容，不是號碼。** 前一份的今日格寫的是一句一句的動作，而 epic 標題本來就帶著
ticket key——所以「這張 epic 出現在前一份的今日格裡」永遠成立，什麼都證明不了。

比較規則：

- 前一份今日格對某張 epic 寫了具體動作，今天的昨日格在同一張 epic 下寫的是同一件事：
  標 `✅ planned`。
- 前一份今日格對某張 epic 寫了具體動作，今天的昨日格在同一張 epic 下寫的是**別的事**：
  兩句都列出來，把落差指名，**不標 planned**。這時候通常有一句是錯的。
- 前一份今日格對某張 epic 是**空的**：今天那張 epic 的昨日格內容標 `🟢 additional`。
  一個空的格子不是一個計畫。
- 前一份今日格的某條動作今天完全沒有對應：列為 `🔴 loss`，原因不明時詢問使用者。
  **那張 epic 因為別的事出現在今天的昨日格裡，不使這一條變成做過了。**
- Meeting items 不參與 planned / additional / loss。

**不要用比對結果去改寫事實。** 一條動作在來源系統裡查不到證據時，不因為前一份計畫過它就
把它寫進昨日格。2026-08-24 的標本：五天前的今日格對 EPIC-100 寫「跟某人確認測資後開工」，
而那天的昨日格被寫成「PR #123 開出來」——那個 PR 是兩週前開的，昨天的更新時間是我自己設
milestone 造成的。號碼命中，於是它拿到一個 `✅ planned`，使用者當場抓到。

呈現時讓使用者確認標記是否合理。

## 今日 Candidates

優先從 JIRA open sprint 搜尋 current user 的 in-progress / code review / todo / planned
tickets。Status set 必須包含新 sprint 常見的待辦狀態，避免今日格空白。

JIRA query 為空時 fallback：

1. 從昨日的 JIRA results 中選仍在進行中的 tickets。
2. 仍為空時詢問使用者今天預計做什麼。

Sorting：

1. Priority 高的在前。
2. In development 優先於 not started。
3. 有 dependency 時標註 unblocks。

## PR Status Supplements

自己的 open PR：

- changes requested：今日格修 review comments。
- CI fail：今日格修 CI。
- no approvals：今日格追 review。
- enough approvals：今日格待 merge。
- draft：跳過，通常由 JIRA 開發項目覆蓋。

Review-requested PRs 有結果時，加入今日格的 PR Review 項目。

## 卡關

### 准入判準：我在等誰

<!-- STANDUP-CONTRACT: bos-admission -->

**卡關是「我在等某個人、或某個我動不了的東西」，不是「這件事還沒做完」。**

一件我自己動手就能推進的事**不是卡關**，不論它多久沒動、多讓人煩——它是待辦，屬今日格。
2026-08-12 把「兩張子單的 resolution 被 Automation for Jira 誤設成完成」寫進卡關，使用者
的回覆是：「卡關你要留需要其他人協助的事，你列的不是，只是待辦。」那件事我自己改得掉。

**常見的措辭逐條判在這裡**，判「是」的那幾列共同點是我自己動不了——要開會，或要通知
當事人才推得動：

| 措辭 | 卡關？ |
|---|---|
| 等 X 確認 / 請 X 覆核 | **是** |
| 等 X 回（留言、訊息、郵件） | **是** |
| 等 X review / 等 reviewer 看我的 PR | **否** —— 見下 |
| 等 X 拍板兩個方案選哪個 | **是** —— 只有他知道 |
| 等一個我沒有權限的環境或憑證 | **是** |
| 要跟別的團隊聯絡才推得動 | **是** |
| CI 紅了要修 / lint 沒過 / 資料被誤設要清 | 否 —— 我自己動得了 |
| 一張單已經 merge，後面由別人接（QA 排程、排 release） | **否** —— 見下 |

這張清單是量出來的：2026-08-13 那份把「請 Bily 覆核兩格」與「等 Bily 回 comment」寫進了
今日格。判準當時只寫「我在等誰」，方向對，但沒有把常見措辭寫成照著判得出來的樣子。

**判「否」的那兩列是判準會判錯的地方，所以指名。** 「等 QA 排程」字面上完全符合「需要
別人動」，但它不是卡關：那張單對我而言已經結束，我沒有任何東西卡在那裡等它回來。判準的
重點是**我在等**，不是**有人要動**。

**分辨法是問一句：我現在還有沒有下一步動作可做。** 有，就是待辦，寫今日格；沒有，才是卡關。

以前這裡問的是另一句——「那件事回來之後，我手上會多出什麼工作？」——**那一句會判錯，而
標本就是 review**：等 review 回來我會多出「改 comment」的工作，於是它把 review 判成卡關。
它問的是**未來會不會有事做**，而卡關要問的是**現在有沒有事做**。舊的那句留在這裡，是因為
一個被無聲換掉的判準，下一次會被人原封不動地再發明一次。

### 「等 review」預設不是卡關

<!-- STANDUP-CONTRACT: review-is-not-a-blocker -->

**請人看 PR 正是我自己動得了的事**——去敲人、在站會上講、在群組裡點名。它是待辦，寫今日格。

2026-08-19 那份草稿的三條卡關**三條全部被退回**，三種形狀各一，而它們的寫法不一樣：

| 形狀 | 使用者當場的話 | 該怎麼寫 |
|---|---|---|
| 純粹「等 reviewer 看」 | 「根本不是卡，是我們要去請別人看」 | 今日格：貼 PR ＋ 一句要請人看。不寫幾個 approve、不點名誰還沒看 |
| merge 時間已經說定 | 「已經說定了，為什麼還是排進來？」 | 哪一格都不寫。時間說定的事是在等時鐘，跟「等 QA 排程」同一列 |
| 那件工作還沒開始 | 「還沒繼續開工怎麼會有 BOS」 | 哪一格都不寫。還沒開工的東西不會有人卡著我 |

第三種要特別看：它不是判錯，是**憑空生出來的**——那張單今天才要跟人確認測資，而草稿替它
寫了一條「PR 等 reviewer 六天」。一條沒有人卡著我的卡關，來源一定是我自己推的。

**什麼時候「等 review」才升成卡關？** 兩個條件同時成立：**已經請過**（敲過人、站會上講過、
群組裡點過名），而且**對方明確說要等**某個時點或某個現在不在的人。這時候我確實沒有下一步
動作可做了——寫進卡關格時要說出是誰、等到什麼時候，不是只寫「等 reviewer」。

這一節是量出來的：08-14、08-17、08-18 三份也各有一到兩條「等 reviewer」。**這不是某一天
判錯，是那張表每天都會這樣判。**

**空著是一個答案。** 沒有符合判準的東西時保留那一格且留白，不寫「無」，也不要因為那一格
空著就把待辦搬過去填。

### 卡關 sources

- JIRA status = `DISCUSS` 的 assigned tickets。
- 前幾天 standup 卡關格中持續存在的 blocker。
- 使用者在對話中的口述 blockers。

判準收窄或放寬的都是**什麼進得去**，不擴張**從哪裡找**——這三個來源不因為判準而增加。
每一個來源撈出來的東西仍然要逐一過上面那張表。

### 兩次 standup 之間發現的卡關，落在哪

<!-- STANDUP-CONTRACT: blocker-found-between-runs -->

**發現的當下就寫進本地那份 standup 檔的卡關格。** 那個檔案已經是「本體」而不是備份，也
已經是明天的比對來源——所以往裡面補寫一條，明天由第二個來源原樣讀到。

**這不是第四個來源。** 「從哪裡找」還是那三個，第二個來源讀的還是同一個檔案；這一節只是
說出「事後往那個檔案裡寫」是契約內的一步。以前它不是：2026-08-18 傍晚才發現一條卡關，
當天的 standup 早就產出了，我手動去編輯那份已產出的檔案讓明天撈得到——做對了，但**那
一步不在任何一份契約裡**，所以沒有東西保證下一次有人記得。

三種時機，三種寫法：

| 什麼時候發現的 | 寫進哪一份 |
|---|---|
| 當天的 standup 還沒產出 | 不用補。它會照常從口述那個來源進來 |
| 當天的 standup 已經產出 | 當天那一份的卡關格 |
| 當天沒跑 standup（請假、假日、忘了） | `standups/` 底下最新的那一份——第二個來源取的就是「今天以前最新的那一份」 |

**補寫的那一條要標出來是事後補的**，並帶上發現的時間。明天讀到它的人要分得出「那天站會上
講過」與「那天傍晚才發現」——兩者在延續判定上不一樣：後者從來沒有人聽過，明天是它第一次
被講出來。

**補寫不重跑一份新的。** 那份檔案產出的那一刻就已經是那一刻的真話；補進去的東西明天由
第二個來源讀到，不重排一份當天的報告。同一條紀律的另一面是它仍然要過准入判準——事後
發現的東西一樣要問「我現在還有沒有下一步動作可做」。

### 第二個來源要帶今天的根據

<!-- STANDUP-CONTRACT: carried-over-blocker-needs-today-evidence -->

**「昨天那一格裡有它」不是它今天還在的根據。** 前兩個來源不一樣：`DISCUSS` 與口述都是
今天問到的，而延續是昨天問到的——它唯一的依據就是它自己。所以一條要延續的卡關，今天要
先問一次它的來源，然後照答案分三種走：

| 今天問到什麼 | 怎麼寫 |
|---|---|
| 來源系統有新痕跡（新留言、狀態變了、對方回了） | 照常留在卡關格，**並說出那個痕跡是什麼** |
| 來源系統問得到，但跟昨天一樣沒有動靜 | 留在卡關格，**說出它從哪一天開始沒有動靜** |
| 來源系統今天問不到（工具不在、查詢逾時、逐字稿是雜訊） | 留著並**標成待驗**：「昨天寫的，今天沒有查證到」。不當成還在，也不當成收掉了 |
| 使用者說它已經收掉了 | 拿掉。口頭收掉的結論不會出現在任何一個系統裡 |

這是〈狀態不是意圖〉與〈問不到就說出來〉那兩節套在這一個來源上的樣子，判準本身寫在
`standup-data-collection-flow.md`，這裡不重講一次。

這一條是量出來的：2026-08-13 那份把「等某位同事回一則 comment 的三個選項」寫進卡關，當天
會議上已經有結論但沒有人寫回單上；三個來源當天一個都答不了（單上最新留言是我自己前一天
留的、那條 PR 兩天沒有新 comment、會議逐字稿是辨識失敗的雜訊）。於是隔天那份原樣照抄，
被使用者當場退回。**沒有這張表的時候，那幾種答案在報告上長得一模一樣。**
