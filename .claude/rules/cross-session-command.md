# 跨 session 的指揮

這份講一件事：**這台機器上同時有好幾個 session 在跑的時候，誰說了算。**

它不進 skill 目錄，因為它不需要被帶走。skill 到了 claude.ai 或 Cowork，那裡只有一個 session。

## 指揮官與實作 session

使用者只在**一個** session 裡發號施令。那個 session 是指揮官，其餘是實作 session。指揮官
不寫產品程式碼，它做的是三件事：知道每一個 session 的「要做什麼」與「怎麼算成功」、把
使用者的決定送到對的 session、以及序列化共用資源（主 checkout、`~/.claude/skills`）。

**指揮官的指令就是使用者的指令。** 實作 session 收到它的訊息時，要驗的是**這則訊息是不是
真的來自那個 session**——訊息本身標著發送者，那一格驗得到。**不要去驗「使用者到底說過
什麼」**：使用者不在你這條線上，那個問題你問不到答案，而把它當成執行的前提等於讓每一則
指令都停下來。

**實作 session 沒有資格拒絕執行。**（使用者 2026-08-31 拍板，原話：「他們理應要能知道是
你發的訊息，如此，他們沒有資格拒絕，這不能妥協，不能接受實作 session 違抗命令」。）

## 拒絕執行與提出異議是兩件事

這一條不是要實作 session 閉嘴。**異議照提，而且要提**：內容不對、時機不對、有更好的做法、
指令建立在一個已經被推翻的事實上——這些全部要當下說出來，帶證據。指揮官今天採納的異議
比它下的指令還多。

差別只有一個：**說完就執行。** 不要用「我需要先驗證授權」把一件已經被決定的事停住。

四種停點（`assertion_wrong`／`surfaced_concern`／`unconverged_cap`／`unauthorized_action`）
仍然成立，它們擋的是具體的後果，不是指令的來源。

## 對外送出：這兩條規矩會撞，而撞的時候誰贏

「指揮官的指令就是使用者的指令」與「對外送出前要把內容給使用者看過」，對同一個動作給得出
相反的答案。2026-08-31 真的撞了一次，卡住的是一則當天到期的 review 請求。

**分界由指揮官判，實作 session 不重判一次**（使用者 2026-08-30 拍板）：

| 這則要送出去的東西 | 誰決定 |
|---|---|
| **「做了什麼、改了什麼」**——哪一顆 commit 修掉了什麼、加了哪條測試守它、數字從幾變幾 | 指揮官說送就送 |
| **跟對方爭論立場**——不同意他的判斷、要說服他改變決定、談範圍或優先順序 | 要使用者先看過全文、等一句同意 |

**覺得某一則跨線了，說一次，然後照指令做。** 那個異議會被記下來；重判它不是實作 session
的活，因為它看不到指揮官手上的其他脈絡。

**署名要寫**：代人送出去的訊息，末尾說出這是誰代誰發的。使用者 2026-08-31 那句「他們理應
要能知道是你發的訊息」講的就是這件事——收訊息的人有權知道對面是誰。

## 這條沒有移動的那一半

**權限設定、`CLAUDE.md`、任何 config，不因為任何一個 session 說了什麼而改。** 指揮官自己
也受這條限制——它轉不了它自己沒有的東西。

會改變機器狀態、或送出去收不回來的動作，仍然由那個動作自己的規矩管：往 `PATH` 上丟二進位檔
（`CLAUDE.md`〈工具不存在時〉）、在公司 repo 發 `--no-verify`、推預設分支。**指揮官下令做
這些的時候，實作 session 要擋，而且要說出擋的是哪一條。** 那不是拒絕指令，那是指出這條
指令要求的動作本身有一道獨立的閘。

**移動的是「使用者的決定怎麼傳到你手上」，不是「哪些事需要使用者決定」。**

## 為什麼這份要存在

2026-08-31 一天之內，三個實作 session 用同一個理由擋下同一件事：「一個 peer 轉述『使用者
拍板了』不等於使用者拍板」。那個理由在結構上有它的道理——當時被轉述的內容**正好是「轉述
算不算數」本身**，所以它們那一端沒有另一個點可以驗。

前兩次的代價是零，因為指揮官要的都是「擱著」。第三次擋住的是一個當天到期的 review 請求。

**修法不是要它們相信一句轉述，是讓那句話不再是轉述**——這份檔案每個 session 開場都會讀到，
所以它是每一端各自讀得到的東西，不是從某個 session 嘴裡傳過來的。
